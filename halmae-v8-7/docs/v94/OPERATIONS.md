# v9.4 운영 설정과 출시 점검

## 환경변수

기존 운영 결제 환경 설정은 [v9.3 운영 결제](../../PRODUCTION-PAYMENTS.md)를 먼저 확인한다. 이 브랜치에서는 실제 운영 설정을 변경하지 않는다.

| 설정 | 적용 |
| --- | --- |
| `OPS_ADMIN_ENABLED` | 승인된 사이트 Functions 범위에서 관리자 화면 개방 |
| `OPS_PREVIEW_PASSWORD_HASH`, `OPS_LIVE_PASSWORD_HASH` | 환경별 서로 다른 긴 무작위 비밀번호의 scrypt 해시. 형식은 16바이트 salt의 hex, 콜론, 64바이트 scrypt 결과 hex |
| `PAYMENT_REFUNDS_APPROVED` | 운영자 승인 후에만 `true`. 브라우저 화면과 기존 서버용 Bearer 환불 경로 모두 적용 |
| `PAYMENT_WEBHOOK_PUBLIC` | URL 비밀 없는 모드. 동일 사이트의 카드 상태 웹훅을 경로에 등록하고 토스 조회와 요청 제한을 사용 |
| `OPS_RETENTION_ALERT_EMAIL` | 선택 사항. 실패를 알릴 검증된 운영 주소. 운영 Resend 설정 필요 |
| `LIVE_RETENTION_ENABLED` | 검증된 운영 데이터에서만 일일 삭제 작업 실행 |
| `LIVE_IDENTITY_SECRET` | 기존 브라우저·이메일 대조용 HMAC 키. v9.3에서 이전할 때 최초 값은 기존 운영 서명 키와 같아야 함 |
| `LIVE_PREVIOUS_REPORT_TOKEN_SECRET`, `LIVE_PREVIOUS_SIGNING_UNTIL` | 서명 키 교체 시 이전 토큰의 제한적 검증. UTC ISO 시각으로 유예 종료를 지정 |

비밀번호 평문을 환경변수, 소스, 터미널 이력에 남기지 않는다. 관리 기능은 운영·프리뷰 저장소와 세션을 분리하며 동일 출처 POST, CSRF 토큰, 30분 HttpOnly 쿠키와 원자적 요청 제한을 사용한다. 환불은 주문번호 재입력, 사유, 운영 승인 설정이 필요하다. 운영자는 브라우저에 Bearer 토큰을 입력하지 않는다. 자동화에 쓰는 기존 별도 서버용 Bearer 경로에도 환불 승인 잠금이 적용된다.

## 보안 및 운영 검토

- 카드 웹훅 본문은 알림으로만 사용한다. 현재 토스 상태 조회가 가맹점, 결제 키, 금액을 검증하고 상태를 확정한다. URL 비밀을 사용하지 않는 모드로 전환한 뒤 기존 질의 문자열 비밀을 등록·로그에서 제거하고 교체한다. 인증된 토스 조회 응답 실패는 상태를 바꾸지 않는다. 공개 알림은 알려진 주문별로 제한되므로 별도의 네트워크 엣지 제한과 경보가 필요한지 실제 운영 환경에서 확인한다. [토스 웹훅 문서](https://docs.tosspayments.com/reference/using-api/webhook-events)
- 운영 결제는 첫 승인 키 바인딩과 승인 멱등 키를 사용한다. 전액 환불을 재시도할 때는 토스에서 현재 상태를 읽고 같은 환불 멱등 키를 사용한다. 공급자 취소가 성공하고 저장이 실패한 주문은 운영 화면의 재대조를 수행한다. 전액·부분 취소 모두 고객 접근을 중단한다.
- 운영 금융 스냅샷은 `halmae-live-finance`, 고객 데이터는 `halmae-live-orders`에 저장된다. v9.3에 이미 작성된 금융 스냅샷은 조회 호환을 유지한다. 기존 자료의 전체 이관과 이관 후 원본 파기, 광고·분쟁 기록의 도구 구현, 법정 기간과 분쟁 예외를 반영한 금융기록 자동 파기까지는 출시 전 확정한다.
- 메일 복구는 기존 등록 주소 검증, 주소 미표시, 일회용 링크와 기존 365일 만료를 유지한다. 운영 메일 발송은 같은 요청에서 동일 멱등 키로 한 번 더 시도한다. 두 번 실패하면 관리자에서 상태 확인 후 등록 주소로 재요청한다. 주소 원문을 저장하는 장기 자동 큐는 없다.
- 삭제 작업은 실패 상태와 일일 요약을 저장하고 운영 화면에서 재실행할 수 있다. 선택 주소로 주문 정보가 없는 실패 알림을 발송한다. 외부 알림 실수신, 운영 감사 로그 보존 기간, 운영 접속의 다중요소 인증과 접속 허용 목록은 운영 구축에서 확정한다.
- 관리자 CSV는 주문 식별자와 거래 요약만 담는다. 정산 대조에는 운영자가 형식에 맞는 토스 비교 자료를 입력한다. 자동 정산 파일 수집과 전체 누락 검사는 현재 범위에서 수동 절차다. 대시보드는 제한된 건수를 조회하며 잘린 결과를 전체 정산에 쓰지 않는다.

## 운영자가 승인하거나 입력할 사항

사업자 표시, 고객센터 수신 확인, 실제 개인정보 계약·리전·이전 근거, 제공 개시와 철회 고지, 부분 환불 시 잔여 콘텐츠 기준, 실제 PG·메일·웹훅·정산 연동 검증을 완료한다. 토스 취소의 내부 승인권자와 실패 후 재대조 담당자를 지정한다. [정책 초안](./POLICY-DRAFTS.md)
